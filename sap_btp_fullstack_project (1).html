Step 03 · Phase 1 — Setup
Data Model (CDS)
Define entities — these become HANA tables, OData entities, and CRUD APIs automatically.
3.1
db/schema.cds — Define all entities
CODE ▶
⚡ Why each decision
  • namespace my; — namespaces prevent name collisions when multiple services share the same DB
  • : managed — built-in CAP aspect that auto-adds createdAt, createdBy, modifiedAt, modifiedBy
  • Association to — loose reference (like FK). Customer exists independently
  • Composition of many — strong ownership. Line items cannot exist without an Order. Enables deep insert and cascading delete
  • @odata.draft.enabled — enables auto-save draft feature (users won't lose data if they close the tab)
📄 db/schema.cds
db/schema.cds
// Namespace groups all our entities under 'my' namespace my; // ── ORDER STATUS enum ───────────────────────────── // Using enum instead of plain String prevents typos // and makes the API self-documenting type OrderStatus : String enum { DRAFT = 'DRAFT'; SUBMITTED = 'SUBMITTED'; APPROVED = 'APPROVED'; REJECTED = 'REJECTED'; CANCELLED = 'CANCELLED'; } // ── CUSTOMERS ──────────────────────────────────── // 'managed' adds createdAt, createdBy, modifiedAt, modifiedBy // CAP fills these automatically — no handler code needed entity Customers : managed { key ID : UUID; name : String(100) @mandatory; email : String(200); phone : String(50); city : String(100); country : String(2); // ISO country code: 'IN', 'US' } // ── ORDERS ─────────────────────────────────────── @odata.draft.enabled // enable auto-save draft entity Orders : managed { key ID : UUID; orderNo : String(20) // human-readable order number @readonly; // set by server, not client customer : Association to Customers; // loose ref — customer exists independently status : OrderStatus default 'DRAFT'; description : String(500); currency : String(3) default 'INR'; // Composition = Orders OWNS the items (cascade delete, deep insert, draft) items : Composition of many OrderItems on items.order = $self; // Calculated field — done by database (no JS needed) totalAmount : Decimal(15,2) @Core.Computed // tells UI this is read-only, server-computed @readonly; } // ── ORDER LINE ITEMS ────────────────────────────── entity OrderItems { key ID : UUID; order : Association to Orders; // back-reference to parent product : String(200) @mandatory; quantity : Integer default 1; unitPrice : Decimal(15,2); // Calculated by DB: quantity * unitPrice lineTotal : Decimal(15,2) = quantity * unitPrice; }
✅
What CAP auto-generates from this file: HANA tables (in production), SQLite tables (locally), OData V4 entity types, CRUD API endpoints, $metadata document. Zero manual SQL or API code.
Step 04 · Phase 2 — Backend
Service Layer (CDS)
Define what is exposed as an OData API and lock it down with authorization.
4.1
srv/service.cds — OData service definition
CODE ▶
⚡ Why
The service layer is the API contract. It decides which entities are exposed, which fields are visible, and who can do what. The DB entity is private — the service is what the outside world sees.
📄 srv/service.cds
srv/service.cds
using { my } from '../db/schema'; // ──────────────────────────────────────────────── // @requires: 'authenticated-user' means: // → ANY logged-in user can reach the service // → individual entity @restrict handles fine permissions // ──────────────────────────────────────────────── service OrderService @(requires: 'authenticated-user') { // ── Customers ────────────────────────────────── // Everyone can read customers, only Managers can write entity Customers @(restrict: [ { grant: 'READ', to: 'OrderViewer' }, { grant: ['CREATE','UPDATE','DELETE'], to: 'OrderManager' } ]) as projection on my.Customers; // ── Orders ───────────────────────────────────── // Draft is inherited from the DB entity (@odata.draft.enabled) // Viewers can READ, Managers can CREATE/UPDATE // where clause: Viewers only see their OWN orders entity Orders @(restrict: [ { grant: 'READ', to: 'OrderViewer', where: 'createdBy = $user' }, // row-level filter! { grant: 'READ', to: 'OrderManager' }, { grant: ['CREATE','UPDATE'], to: 'OrderManager' }, { grant: 'DELETE', to: 'OrderManager' } ]) as projection on my.Orders; // ── Order Items ──────────────────────────────── entity OrderItems @(restrict: [ { grant: 'READ', to: 'OrderViewer' }, { grant: ['CREATE','UPDATE','DELETE'], to: 'OrderManager' } ]) as projection on my.OrderItems; // ── Custom Actions ───────────────────────────── // Bound action: called on a specific Order instance // POST /Orders(ID)/OrderService.submitOrder action submitOrder(orderId: UUID) returns Orders; action approveOrder(orderId: UUID) returns Orders; action rejectOrder(orderId: UUID, reason: String) returns Orders; // Unbound function: no specific Order needed // GET /OrderService/getOrderStats() function getOrderStats() returns { total: Integer; draft: Integer; submitted: Integer; approved: Integer; totalValue: Decimal; }; }
Step 05 · Phase 2 — Backend
Business Logic — srv/service.js
Event handlers for validation, computed fields, and custom actions.
5.1
srv/service.js — Complete handler file
CODE ▶
⚡ Handler phases explained
  • before — runs BEFORE the DB operation. Use for: input validation, enriching req.data (e.g. generating orderNo)
  • on — REPLACES the default DB operation. Use for: fully custom logic
  • after — runs AFTER the DB operation. Use for: computing derived fields (totalAmount), sending notifications
📄 srv/service.js
srv/service.js
// cds = the main CAP runtime object const cds = require('@sap/cds'); // module.exports = class pattern = the CAP-recommended way // 'this' inside refers to the service instance module.exports = class OrderService extends cds.ApplicationService { async init() { // ── DB entity refs (shorthand for SELECT/INSERT/UPDATE) ── const { Orders, OrderItems, Customers } = this.entities; // ════════════════════════════════════════════ // BEFORE handlers — validate BEFORE DB write // ════════════════════════════════════════════ // Generate order number and set defaults before CREATE this.before('CREATE', 'Orders', async (req) => { // Generate a human-readable order number: ORD-20241115-0001 const today = new Date().toISOString().slice(0,10).replace(/-/g, ''); const count = await SELECT.one`SELECT count(*) as cnt FROM my_Orders`; req.data.orderNo = `ORD-${today}-${String((count?.cnt || 0) + 1).padStart(4,'0')}`; // Validate: customer must be provided if (!req.data.customer_ID) { return req.error(400, 'Customer is required to create an order'); } }); // Validate line items before saving this.before(['CREATE','UPDATE'], 'OrderItems', (req) => { if (req.data.quantity !== undefined && req.data.quantity <= 0) { return req.error(400, 'Quantity must be greater than 0'); } if (req.data.unitPrice !== undefined && req.data.unitPrice < 0) { return req.error(400, 'Unit price cannot be negative'); } }); // ════════════════════════════════════════════ // AFTER handlers — enrich response AFTER DB read // ════════════════════════════════════════════ // Compute totalAmount after every READ of Orders // We calculate from items because lineTotal is DB-computed this.after('READ', 'Orders', async (orders, req) => { if (!orders || orders.length === 0) return; // Handle both single object and array (READ vs READ by key) const list = Array.isArray(orders) ? orders : [orders]; for (const order of list) { if (!order.ID) continue; const result = await SELECT.one .from('my.OrderItems') .columns('sum(lineTotal) as total') .where({ order_ID: order.ID }); order.totalAmount = result?.total ?? 0; } }); // ════════════════════════════════════════════ // CUSTOM ACTIONS // ════════════════════════════════════════════ this.on('submitOrder', async (req) => { const { orderId } = req.data; try { // Load the order const order = await SELECT.one.from(Orders).where({ ID: orderId }); if (!order) return req.error(404, `Order ${orderId} not found`); // Business rule: only DRAFT can be submitted if (order.status !== 'DRAFT') { return req.error(409, `Cannot submit an order in status: ${order.status}`); } // Validate: must have at least one item const items = await SELECT.from(OrderItems).where({ order_ID: orderId }); if (!items || items.length === 0) { return req.error(422, 'Cannot submit: order has no line items'); } // Update status await UPDATE(Orders).set({ status: 'SUBMITTED' }).where({ ID: orderId }); // Return updated order return await SELECT.one.from(Orders).where({ ID: orderId }); } catch(err) { req.logger.error('submitOrder failed:', err); return req.error(500, 'Unexpected error during submit'); } }); this.on('approveOrder', async (req) => { const { orderId } = req.data; const order = await SELECT.one.from(Orders).where({ ID: orderId }); if (!order) return req.error(404, 'Order not found'); if (order.status !== 'SUBMITTED') return req.error(409, 'Only SUBMITTED orders can be approved'); await UPDATE(Orders).set({ status: 'APPROVED' }).where({ ID: orderId }); return await SELECT.one.from(Orders).where({ ID: orderId }); }); this.on('rejectOrder', async (req) => { const { orderId, reason } = req.data; const order = await SELECT.one.from(Orders).where({ ID: orderId }); if (!order) return req.error(404, 'Order not found'); await UPDATE(Orders) .set({ status: 'REJECTED', description: reason || order.description }) .where({ ID: orderId }); return await SELECT.one.from(Orders).where({ ID: orderId }); }); this.on('getOrderStats', async (req) => { const stats = await SELECT` SELECT count(*) as total, sum(case when status='DRAFT' then 1 else 0 end) as draft, sum(case when status='SUBMITTED' then 1 else 0 end) as submitted, sum(case when status='APPROVED' then 1 else 0 end) as approved FROM my_Orders WHERE IsActiveEntity = true `; return stats[0] || { total:0, draft:0, submitted:0, approved:0, totalValue:0 }; }); // Always call super.init() — registers default CRUD handlers await super.init(); } };
⚠️
Critical: Always call await super.init() at the END of your init(). If you call it at the start, the default CRUD handlers will overwrite your custom handlers.
Step 06 · Phase 2 — Backend
Security — XSUAA Configuration
Define scopes, role templates, and role collections for JWT-based authorization.
6.1
xs-security.json — XSUAA definition
SECURITY ▶
⚡ The 3-tier model
  • Scope — smallest unit of permission. Goes inside the JWT token. Example: OrderViewer
  • Role-Template — groups scopes. Example: OrderViewerRole contains the OrderViewer scope
  • Role-Collection — what admins assign to actual users in BTP Cockpit
📄 xs-security.json
xs-security.json
{ "xsappname": "order-app", // "dedicated" = one XSUAA instance per BTP subaccount // "shared" = multi-tenant (used for SaaS apps) "tenant-mode": "dedicated", "scopes": [ { "name": "$XSAPPNAME.OrderViewer", // $XSAPPNAME is replaced by XSUAA with the actual app name at runtime // This prevents scope collisions across multiple apps "description": "Can read orders and customers" }, { "name": "$XSAPPNAME.OrderManager", "description": "Can create, update, approve/reject orders" } ], "role-templates": [ { "name": "OrderViewer", "description": "View orders only", "scope-references": ["$XSAPPNAME.OrderViewer"] }, { "name": "OrderManager", "description": "Manage all orders", // Manager gets BOTH viewer and manager scopes "scope-references": [ "$XSAPPNAME.OrderViewer", "$XSAPPNAME.OrderManager" ] } ], "role-collections": [ { "name": "Order Viewer", "description": "Assign to read-only users", "role-template-references": [ "$XSAPPNAME.OrderViewer" ] }, { "name": "Order Manager", "description": "Assign to managers who approve orders", "role-template-references": [ "$XSAPPNAME.OrderManager" ] } ] }

Quick Reference
Common Errors & Fixes
The most frequent issues developers hit and exactly how to fix them.
E1
401 Unauthorized after deployment
SECURITY ▶
  • Check: cf env order-app-srv — is xsuaa in VCAP_SERVICES? If not → bind: cf bind-service order-app-srv order-app-xsuaa
  • Check: Decode JWT at jwt.io. Is iss matching your XSUAA URL? Is exp in the future?
  • Check: Did xsappname in xs-security.json change? Old tokens have old scope prefix → users must re-login
  • Fix: cf restage order-app-srv after binding a service
E2
403 Forbidden — user logged in but gets no data
SECURITY ▶
  • Cause: User is authenticated but has no role-collection assigned
  • Fix: BTP Cockpit → Security → Role Collections → assign Order Manager or Order Viewer to the user
  • Check: Decode JWT — look for scope array. Should contain order-app!t123.OrderViewer
E3
cds watch — "No model loaded" error
CODE ▶
  • Cause: CDS syntax error in one of your .cds files
  • Fix: Check terminal output for the exact file and line number. Common mistakes: missing semicolon, typo in entity name, wrong using path
  • Debug: Run cds compile db/ srv/ --to json to see full error details
E4
HANA deployment fails — SQL errors in cf logs
DATA ▶
  • Check logs: cf logs order-app-db-deployer --recent
  • Common cause: Trying to change a column type or drop a column with data in it
  • Fix for column rename: Create a new column, migrate data, then drop old — never rename directly
  • Fix for type change: Same pattern — new column, migrate, drop old
  • Nuclear option (dev only): cf delete-service order-app-db then redeploy — DESTROYS all data
🚨
Never run delete-service in production. It permanently deletes all tenant data in the HDI container with no recovery option.
E5
Fiori Elements shows blank page / no data
UI ▶
  • Step 1: Open DevTools → Network → check if OData request is going to the right URL
  • Step 2: Check if the OData service path in manifest.json matches the actual CAP service path
  • Step 3: Press Ctrl+Shift+Alt+P in the Fiori app → UI5 Diagnostics → check model binding
  • Step 4: Verify annotations compiled: cds compile srv/ --to json | grep LineItem
