What is SAP BTP? — Basics
Fundamental questions every interviewer asks first.
What is SAP BTP and why is it used?Basic
  • BTP stands for Business Technology Platform — it is SAP's cloud platform
  • It is used to build, extend, and integrate enterprise applications
  • Think of it as SAP's version of AWS or Azure — but focused on business applications
  • It connects SAP systems (like S/4HANA) with custom applications and third-party tools
  • It provides ready-to-use services: database (HANA), security (XSUAA), messaging (Event Mesh), and more
  • Companies use it to extend standard SAP without modifying the core system
  • It runs on multiple cloud providers: AWS, Azure, Google Cloud, and SAP's own data centers
What are the main components/services of SAP BTP?Basic
  • CAP (Cloud Application Programming model) — framework for building services and APIs
  • SAP HANA Cloud — managed in-memory database for storing application data
  • XSUAA — security service for user login, roles, and permissions
  • Cloud Foundry — platform to deploy and run Node.js/Java applications
  • SAP Event Mesh — messaging service for async communication between apps
  • Destination Service — central place to store connection details to external systems
  • Connectivity Service — secure tunnel to reach on-premise (behind firewall) systems
  • SAP Integration Suite (CPI) — tool for connecting SAP and third-party systems
  • SAP Build / Fiori Launchpad — user interface and app hosting layer
  • SAP Cloud SDK — library to call SAP APIs (like S/4HANA) easily and safely
What is the difference between SAP BTP and S/4HANA?Basic
  • S/4HANA is an ERP system — it manages core business processes like finance, procurement, HR
  • SAP BTP is a development platform — it is used to build custom apps, extensions, and integrations
  • I do not modify S/4HANA directly — instead I build apps on BTP that connect to S/4HANA via APIs
  • S/4HANA = the house. BTP = the workshop where I build extensions and additions to the house
  • BTP uses SAP Cloud SDK and Destination Service to securely call S/4HANA APIs
What is the BTP Cockpit and what do I do in it?Basic
  • BTP Cockpit is the web-based admin console for managing everything on SAP BTP
  • I use it to create and manage Subaccounts — each subaccount is like an isolated environment
  • I create Service Instances — e.g., create a HANA Cloud instance, an XSUAA instance
  • I manage Role Collections — assign permissions to users
  • I configure Destinations — connection details for external systems like S/4HANA
  • I set up Cloud Foundry Spaces — dev, QA, and prod spaces for deploying apps
  • I monitor apps — view memory usage, running instances, and logs
  • I set up Trust configurations — linking Identity Providers like Azure AD or IAS
What is a Subaccount, Global Account, and Directory in BTP?Basic
  • Global Account — the top-level contract with SAP. One per company. Contains all resources and quota
  • Directory — optional grouping folder inside a global account. Used to organize subaccounts by region or department
  • Subaccount — the actual working unit. I deploy apps here. Each subaccount has its own Cloud Foundry environment
  • Typical setup: Global Account → Directory (APAC) → Subaccounts (Dev, QA, Prod)
  • Services like HANA Cloud and XSUAA are created inside a subaccount
  • Each subaccount can have a different identity provider and different role assignments
BTP Services — Overview
What each service does and when I use it.
What is SAP HANA Cloud and how is it different from a normal SQL database?Basic
  • SAP HANA Cloud is an in-memory cloud database — data is stored in RAM, not just on disk
  • This makes reads and aggregations extremely fast — 10x to 100x faster than traditional databases for analytics
  • It uses a columnar storage format — stores data column by column (great for analytics) not row by row
  • Normal SQL databases (like MySQL, PostgreSQL) are row-based — better for transactional writes
  • HANA can handle both OLTP (transactions) and OLAP (analytics) in one database — called HTAP
  • It is fully managed on BTP — I do not install or maintain the database server myself
  • CAP applications automatically connect to HANA Cloud using HDI containers
What is XSUAA and why do I need it?Basic
  • XSUAA = Extended Services for User Account and Authentication
  • It is SAP BTP's security service — handles user login, OAuth2 tokens, and permissions
  • Without XSUAA my app would have no security — anyone could call my API
  • XSUAA issues JWT tokens to users after they log in — my CAP service checks this token on every request
  • I define what permissions exist in xs-security.json — scopes, role templates, role collections
  • It integrates with company Identity Providers (like Azure AD) so employees can use their existing login
  • CAP uses XSUAA automatically when I bind the XSUAA service to my application
What is Cloud Foundry and how do I use it on BTP?Basic
  • Cloud Foundry (CF) is an open-source Platform as a Service (PaaS) — it runs my Node.js apps
  • I push my CAP application to CF and it handles containers, networking, scaling, and restart on failure
  • CF organizes apps in Spaces — e.g., dev space, QA space, prod space
  • I deploy using the CF CLI: cf push or via MTA deploy: cf deploy app.mtar
  • CF automatically provides my app with service credentials via VCAP_SERVICES environment variable
  • I can scale horizontally: cf scale my-app -i 3 runs 3 instances of my app
  • CF gives each app a public URL automatically — no need to configure load balancers manually
What is OData and why does SAP use it?Basic
  • OData = Open Data Protocol — a standard REST-based protocol for querying and updating data
  • SAP uses OData because it is standardized — any OData client (UI5, Excel, Power BI) can consume SAP APIs
  • OData supports powerful querying out of the box: filtering ($filter), sorting ($orderby), pagination ($top/$skip), and expanding related data ($expand)
  • CAP generates OData V4 APIs automatically from my CDS entity definitions — no manual coding needed
  • OData V4 is the current version — V2 is older but still needed for some legacy Fiori apps
  • The service metadata is available at: /service-path/$metadata — this is a machine-readable description of all entities and operations
CAP Basics
What CAP is, how it works, and core concepts explained simply.
What is CAP (Cloud Application Programming model)?Basic
  • CAP is SAP's open-source framework for building enterprise apps on BTP
  • It is built on top of Node.js (or Java) — so I write regular JavaScript/TypeScript
  • Main idea: convention over configuration — I define my data model and CAP does the rest
  • I define entities in CDS (Core Data Services) — CAP auto-generates the OData API, DB tables, and CRUD operations
  • Without CAP I would write all API routes, DB queries, auth checks manually — CAP handles all of that
  • It follows a 3-layer architecture: Data Model → Service Layer → Handler Layer
  • It has built-in support for HANA Cloud, SQLite (local dev), XSUAA security, and OData V4
What is CDS (Core Data Services) in simple terms?Basic
  • CDS is a domain-specific language for defining data models and services — think of it like a powerful schema language
  • I write .cds files to define: entities (tables), relationships, services (APIs), and annotations (UI hints)
  • CAP compiles CDS to: SQL tables in HANA, OData metadata XML, and JSON schema
  • Example of a simple CDS entity:
entity Products {
  key ID    : UUID;
  name      : String(100);
  price     : Decimal(10,2);
  category  : String(50);
  createdAt : Timestamp;
}
  • This one definition creates: a HANA table, an OData entity, and CRUD API — automatically
  • CDS also supports annotations — extra hints for Fiori UI like which columns to show in a list page
What is the structure of a CAP project?Basic
  • db/ folder — CDS files for data model (entities, types, aspects). These become HANA tables
  • srv/ folder — CDS files for services (which entities to expose as API) + JavaScript handler files (business logic)
  • app/ folder — UI5 or Fiori Elements front-end applications
  • package.json — Node.js dependencies and CAP configuration (database type, security settings)
  • mta.yaml — deployment descriptor for Cloud Foundry (lists all modules and services)
  • xs-security.json — XSUAA security definition (scopes, roles)
  • .cdsrc.json — CAP configuration overrides for local development
  • To run locally: cds watch — starts a server with hot reload using SQLite in-memory database
What is the difference between a CDS entity and a CDS service?Basic
  • Entity = the data model (like a database table definition). Defined in db/ folder
  • Service = the API layer that exposes entities (or projections of entities) as OData endpoints
  • Entity defines what data exists. Service defines what is accessible via the API
  • A service can expose all fields, selected fields, or a filtered view of an entity
  • Same entity can be exposed in multiple services with different field sets — e.g., a public service and an admin service
// db/schema.cds — data model
entity Products {
  key ID : UUID; name : String; internalCode : String;
}

// srv/service.cds — API layer (hides internalCode)
service CatalogService {
  entity Products as projection on db.Products {
    ID, name  // internalCode NOT exposed
  };
}
What is a projection in CAP and why do I use it?Basic
  • A projection is a view on top of an entity — like a filtered/customized version of it
  • Instead of exposing the raw database entity directly, I create a projection in the service layer
  • Why I use it:
  • Security — hide sensitive fields like internal prices, supplier codes, etc.
  • Performance — only fetch fields that are needed, not all columns
  • Flexibility — rename fields, add computed columns, filter rows
  • I can add WHERE conditions to show only active records
  • I can add computed fields like price * 1.1 as priceWithTax
  • Changes to the DB entity do not automatically expose new fields in the service — gives API stability
What is the difference between Association and Composition in CDS?Basic
  • Association = a loose relationship. Both entities exist independently. Like a reference/foreign key
  • Composition = a strong ownership. Child cannot exist without parent. Parent "owns" the children
  • Simple rule: Does child make sense without the parent? Yes → Association. No → Composition
  • Example: Order has a Customer → Association (Customer exists independently)
  • Example: Order has Line Items → Composition (Line Items belong to the Order)
  • Composition benefits in CAP: deep insert (create order + items in one API call), cascading delete (delete order → items deleted too), and draft support (draft the whole aggregate together)
entity Orders {
  key ID     : UUID;
  customer   : Association to Customers;  // loose ref
  items      : Composition of many OrderItems; // owns items
}
What is a CAP event handler and why do I need it?Basic
  • CAP handles basic CRUD (Create, Read, Update, Delete) automatically — I do not need to write SQL
  • But for custom business logic, I write event handlers in JavaScript
  • Event handlers are functions that run at specific points during request processing
  • There are 3 types:
  • before — runs before the database operation. Use for: validation, input enrichment
  • on — replaces the default operation. Use for: completely custom logic
  • after — runs after the database operation. Use for: enriching the response
// Example: validate before creating an order
this.before('CREATE', 'Orders', (req) => {
  if (!req.data.customerId) {
    req.error(400, 'Customer ID is required');
  }
});

// Example: add label after reading
this.after('READ', 'Orders', (orders) => {
  orders.forEach(o => {
    o.statusLabel = o.status === 'A' ? 'Active' : 'Inactive';
  });
});
CAP Architecture — Deep Dive
App Router, folder structure, request pipeline, multi-tenancy, deployment patterns.
What is the App Router in CAP and why is it needed?Basic
  • The App Router (@sap/approuter) is a Node.js module that acts as the single entry point for all UI requests in a BTP application
  • It sits in front of all your services and UI apps — users never directly hit the CAP backend or HANA
  • What App Router does:
  • Authentication — redirects unauthenticated users to XSUAA login page. Handles OAuth2 authorization code flow
  • Token forwarding — attaches the JWT token to every backend request automatically
  • Routing — routes UI requests to the correct HTML5 module and API requests to the CAP backend via xs-app.json
  • Static file serving — serves UI5/Fiori apps from HTML5 Repository or local files
  • CSRF protection — manages CSRF tokens for OData write operations
  • Session management — handles session cookies for browser-based users
  • Without App Router: you would need to manually implement OAuth2 login flow, token forwarding, and routing in every UI app
  • In MTA deployment: App Router is its own CF module that runs as a separate application
// xs-app.json — App Router routing config
{
  "welcomeFile": "/app/index.html",
  "authenticationMethod": "route",
  "routes": [
    {
      "source": "^/odata/v4/(.*)$",
      "destination": "srv-api",
      "authenticationType": "xsuaa",
      "csrfProtection": true
    },
    {
      "source": "^/app/(.*)$",
      "target": "$1",
      "service": "html5-apps-repo-rt",
      "authenticationType": "xsuaa"
    },
    {
      "source": "^/(.*)$",
      "target": "$1",
      "authenticationType": "none"
    }
  ]
}
Explain the complete CAP request lifecycle from browser to database.Intermediate
  • The full lifecycle of a GET /Orders request from a Fiori UI:
  • 1. Browser → App Router: User accesses the app. App Router checks if user has a valid session. If not → redirect to XSUAA login
  • 2. XSUAA login → User authenticates. XSUAA issues a JWT token with user's scopes
  • 3. App Router → CAP Backend: Routes the request, attaches JWT as Authorization header
  • 4. CAP middleware stack: Parses the OData URL, validates JWT signature via XSUAA public key, checks scopes
  • 5. Handler pipeline: before handlers run, then on handler (or generic), then after handlers
  • 6. CAP Database layer: Builds the SQL query from CDS query and executes it against HANA
  • 7. HANA: Returns result set. CAP converts to OData JSON format
  • 8. Response: Goes back through App Router → Browser. Fiori renders the data
Browser → AppRouter (auth) → CAP srv → [before] → [on/generic] → [after]
                                              ↓
                                        HANA Cloud (SQL)
                                              ↓
                              OData JSON ← CAP ← Results

What is xs-security.json and how do scopes, role-templates, and role-collections work together?Intermediate
  • xs-security.json is the XSUAA security configuration file — defines permissions for my app
  • 3-tier model: Scope → Role-Template → Role-Collection
  • Scope = the smallest permission unit (e.g., Orders.Read, Orders.Write). Scopes go inside JWT tokens
  • Role-Template = groups related scopes into a role (e.g., OrderViewer gets Orders.Read)
  • Role-Collection = groups role-templates. This is what admins assign to actual users in BTP Cockpit
{
  "xsappname": "my-cap-app",
  "tenant-mode": "dedicated",
  "scopes": [
    { "name": "$XSAPPNAME.Orders.Read",  "description": "Read orders" },
    { "name": "$XSAPPNAME.Orders.Write", "description": "Write orders" },
    { "name": "$XSAPPNAME.Admin",        "description": "Full admin access" }
  ],
  "role-templates": [
    {
      "name": "OrderViewer",
      "scope-references": ["$XSAPPNAME.Orders.Read"]
    },
    {
      "name": "OrderManager",
      "scope-references": ["$XSAPPNAME.Orders.Read", "$XSAPPNAME.Orders.Write"]
    },
    {
      "name": "Administrator",
      "scope-references": ["$XSAPPNAME.Admin", "$XSAPPNAME.Orders.Read", "$XSAPPNAME.Orders.Write"]
    }
  ],
  "role-collections": [
    {
      "name": "Order Viewer Role Collection",
      "role-template-references": ["$XSAPPNAME.OrderViewer"]
    }
  ]
}
  • In CDS, I use @requires: 'Orders.Read' on a service or entity to enforce the scope
  • CAP reads the JWT on each request and checks if the required scope is present — if not → 403 Forbidden
How does multi-tenancy work in CAP architecture?Advanced
  • Multi-tenancy = one application instance serves multiple customer organizations (tenants), each with complete data isolation
  • CAP's approach — tenant-aware architecture:
  • Each tenant gets their own HDI container in HANA → own schema → complete DB-level isolation
  • The SaaS Provisioning Service on BTP manages tenant onboarding/offboarding lifecycle
  • CAP's cds-mtx (multi-tenancy extensions) library handles tenant routing and schema upgrades
  • The JWT token carries the zid claim — the tenant (zone) ID. CAP routes each request to the correct HDI container based on zid
  • Tenant onboarding flow:
  • Admin subscribes tenant in BTP Cockpit → SaaS Provisioning Service calls CAP's /-/cds/saas-provisioning/subscribe endpoint
  • CAP creates a new HDI container for the tenant and deploys the DB schema
  • Tenant users can now log in and their data is isolated from all other tenants
// package.json — enable multi-tenancy
{
  "cds": {
    "requires": {
      "multitenancy": true,
      "extensibility": true,
      "[production]": {
        "db": { "kind": "hana-mt" },
        "auth": { "kind": "xsuaa" }
      }
    }
  }
}
What is the difference between @restrict and @requires annotations in CAP?Intermediate
  • @requires — service-level or entity-level gate. User must have this scope or the whole service/entity is inaccessible
  • @restrict — fine-grained per-operation authorization. Can restrict specific operations (READ, WRITE, DELETE) per scope/role
// @requires — simple: user must have this scope to access the entity
service OrderService @(requires: 'authenticated-user') {

  // @restrict — granular: different scopes for different operations
  entity Orders @(restrict: [
    { grant: ['READ'],             to: 'Orders.Read'  },
    { grant: ['CREATE','UPDATE'],  to: 'Orders.Write' },
    { grant: ['DELETE'],           to: 'Orders.Admin' },
    // Filter: users only see their OWN orders
    { grant: 'READ', to: 'Orders.Read',
      where: 'createdBy = $user' }
  ]) as projection on db.Orders;
}
  • The where clause in @restrict automatically adds a SQL WHERE filter — users cannot bypass it even by directly calling the API
  • This is called instance-level authorization — controls which rows a user can access, not just which operations
How does local development work in CAP and how does it differ from production?Basic

  • Database: Uses SQLite in-memory locally. Automatically switches to HANA in production via [production] profile in package.json
  • Auth: Uses mock auth locally — just add ?sap-client=100 or use .cdsrc.json to set a mock user with specific roles. No XSUAA service needed
  • Data: CSV files in db/data/ are automatically loaded into SQLite on cds watch
  • Run: cds watch starts the server with hot-reload on every file save

What is cds.env and how does profile-based configuration work?Intermediate
  • cds.env is CAP's configuration system — merges settings from package.json, .cdsrc.json, and environment variables
  • Profile-based config: Different settings for [development], [production], [test] profiles
  • CAP automatically activates the right profile based on NODE_ENV

        "db":   { "kind": "hana" },

  • Environment variable override: CDS_REQUIRES_DB_KIND=hana overrides any JSON setting
What is the SaaS Provisioning Service and how does it work with CAP?Advanced
  • SaaS Provisioning Service (saas-registry) is a BTP service that manages tenant subscription lifecycle for multi-tenant SaaS apps
  • When a new tenant subscribes to your SaaS app via BTP Cockpit:
  • BTP calls the onSubscription callback URL you registered with saas-registry
  • CAP's cds-mtx library handles this callback automatically
  • It creates a new HANA HDI container for the tenant and deploys the latest schema
  • Returns success → tenant can now access the app with their own isolated data
  • When a tenant unsubscribes:
  • The offboarding callback is called → CAP drops the tenant's HDI container (all their data is deleted)
  • This is irreversible — make sure to implement data export before offboarding
  • Schema upgrades across tenants: When you deploy a new version of your app, CAP can upgrade all tenant schemas automatically using cds-mtx's upgrade API

What are custom actions and functions in CAP? Give an example.Intermediate

  • Action = can modify data (HTTP POST). Used for business operations like "submit", "approve", "cancel"
  • Both are defined in CDS and handled in JavaScript
  • Unbound — not tied to a specific entity instance. Called at service level
  • Bound — tied to a specific entity instance. Like calling "approve" on Order with ID=123
// CDS definition
service OrderService {
  entity Orders as projection on db.Orders;

  action submitOrder(orderId: UUID) returns String;

  action Orders.approve() returns Boolean;

  function getOrderStats() returns { total: Integer; amount: Decimal; };
}

  const { orderId } = req.data;
  await UPDATE('Orders').set({ status: 'SUBMITTED' }).where({ ID: orderId });

});
How does deep insert work in CAP?Intermediate

  • Works automatically for Composition relationships in CAP

  • Pitfalls to remember:
  • before CREATE handlers fire once for each child item — can cause N+1 database calls
  • To get the parent ID inside a child handler use req.data.up_
  • Very large payloads (hundreds of children) can hit HANA transaction size limits

How do I handle errors in CAP without crashing the service?Intermediate
  • Use req.error(httpCode, 'message') inside handlers — this is the CAP way to return errors
  • This automatically: rolls back the database transaction + returns the right HTTP error response
  • Use try-catch around external API calls and database operations
  • Log errors using req.logger.error() — this includes the correlation ID automatically
  • Use specific HTTP codes: 400 (bad input), 404 (not found), 409 (conflict), 422 (business rule), 502 (upstream failed)
  • Never expose raw internal errors to users — map them to business-meaningful messages
this.on('submitOrder', async (req) => {
  try {
    const { orderId } = req.data;
    if (!orderId) return req.error(400, 'orderId is required');

    const order = await SELECT.one.from('Orders').where({ ID: orderId });
    if (!order)     return req.error(404, 'Order not found');
    if (order.status !== 'DRAFT') return req.error(409, 'Only DRAFT orders can be submitted');

    await UPDATE('Orders').set({ status: 'SUBMITTED' }).where({ ID: orderId });
    return 'Order submitted';
  } catch(err) {
    req.logger.error('submitOrder failed:', err);
    req.error(500, 'Unexpected error — please contact support');
  }
});
How does CAP handle transactions? When do I create manual transactions?Advanced
  • CAP automatically wraps each incoming request in a database transaction
  • If the handler completes without error → transaction commits automatically
  • If I call req.error() or throw an error → transaction rolls back automatically
  • For multi-step operations where I want explicit control:
const tx = cds.transaction(req);
try {
  await tx.run(INSERT.into('Orders').entries(orderData));
  await tx.run(INSERT.into('AuditLog').entries({ action: 'CREATE' }));
  await tx.commit();
} catch(e) {
  await tx.rollback();
  req.error(500, e.message);
}
  • Warning: Do not use Promise.all with multiple DB operations in the same transaction — can cause deadlocks in HANA if the operations touch overlapping rows
  • Use sequential await instead of parallel for safety

What is the difference between a virtual field and a calculated field in CDS?Intermediate

SAP HANA Cloud — Basics
HDI containers, basic SQL, and how CAP uses HANA.
What is an HDI Container and why does CAP use it?Basic
  • HDI = HANA Deployment Infrastructure — a way to manage database objects declaratively
  • Instead of running CREATE TABLE SQL manually, I define tables as .hdbtable files — HDI deploys them
  • Deployment is idempotent — if the table already exists with correct structure, it is not recreated
  • Each application gets its own HDI container = its own isolated schema in HANA
  • Tenant A's data is in Container A, Tenant B's data is in Container B — completely isolated
  • CAP generates the HDI artifact files automatically during cds build --for hana
  • I deploy them via the MTA: the db module in mta.yaml runs the HDI deployer
  • The HDI container has a technical owner user and a runtime application user with limited privileges
What is the difference between row store and column store in HANA?Basic
  • Column store (default in HANA) — data for each column is stored together on disk/memory
  • Excellent for: reading specific columns across many rows, aggregations (SUM, COUNT, AVG), analytics
  • HANA compresses column data very efficiently — saves memory
  • Row store — data for each row is stored together (like traditional databases)
  • Better for: very high-frequency write operations, reading all columns of one specific row
  • My CAP entities use column store by default — this is correct for most enterprise apps
  • I only use row store for special cases like lock tables, queue tables with very high insert/delete rates
What basic SQL operations do I use in HANA and CAP?Basic
  • In CAP I use the CDS Query Language (CQL) — a JavaScript API that looks like SQL but generates safe parameterized queries
  • SELECT — read data:
// Read all active orders
const orders = await SELECT.from('Orders').where({ status: 'ACTIVE' });

// Read one record
const order = await SELECT.one.from('Orders').where({ ID: orderId });

// Read with expand (join)
const orders = await SELECT.from('Orders').columns('*', 'items(*)');
  • INSERT — create data:
await INSERT.into('Orders').entries({ ID: uuid(), customer: 'C001' });
  • UPDATE — modify data:
await UPDATE('Orders').set({ status: 'APPROVED' }).where({ ID: orderId });
  • DELETE — remove data:
await DELETE.from('Orders').where({ ID: orderId });
How do I create an index in HANA and when should I?Basic
  • An index speeds up queries by pre-sorting data on specific columns — like a book index
  • Without an index, HANA scans every row (full table scan) — slow for large tables
  • With an index, HANA jumps directly to matching rows — fast
  • When to create an index:
  • Columns used in WHERE clauses frequently: WHERE status = 'OPEN'
  • Columns used in JOIN conditions: WHERE o.customer_id = c.id
  • Columns used in ORDER BY: ORDER BY created_at DESC
-- Create an index on STATUS and CREATED_AT columns
CREATE INDEX IDX_ORDERS_STATUS_DATE
ON ORDERS (STATUS, CREATED_AT DESC);

-- Composite index (multiple columns)
CREATE INDEX IDX_ITEMS_ORDER_PRODUCT
ON ORDER_ITEMS (ORDER_ID, PRODUCT_ID);
  • When NOT to create: Columns with very few unique values (like a boolean) — index does not help much
  • Too many indexes slow down INSERT/UPDATE — every index must be updated when data changes

How do I find and fix a slow query in HANA?Intermediate

Write a HANA stored procedure with error handling for bulk processing.Advanced
  • HANA stored procedures use SQLSCRIPT language — similar to SQL but with procedural logic
  • I use CONTINUE HANDLER inside loops so one bad record does not stop the whole batch
  • I use EXIT HANDLER at the outer level to catch unexpected catastrophic errors
CREATE OR REPLACE PROCEDURE PROCESS_BATCH_ORDERS(
  IN  p_batch_id  NVARCHAR(36),
  OUT o_processed INTEGER,
  OUT o_failed    INTEGER
)
LANGUAGE SQLSCRIPT
AS BEGIN
  DECLARE v_count INTEGER := 0;
  DECLARE v_err   INTEGER := 0;

  -- Exit handler for catastrophic errors
  DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN
    o_processed := v_count; o_failed := v_err;
    ROLLBACK;
  END;

  BEGIN TRANSACTION;

  FOR rec AS
    SELECT ID, CUSTOMER_ID, AMOUNT
    FROM STAGING_ORDERS
    WHERE BATCH_ID = :p_batch_id
  DO
    BEGIN
      -- Continue handler: skip bad records instead of stopping
      DECLARE CONTINUE HANDLER FOR SQLEXCEPTION
      BEGIN
        v_err := v_err + 1;
        UPDATE STAGING_ORDERS SET STATUS = 'ERROR' WHERE ID = rec.ID;
      END;

      INSERT INTO ORDERS(ID, CUSTOMER_ID, AMOUNT, STATUS)
      VALUES(rec.ID, rec.CUSTOMER_ID, rec.AMOUNT, 'NEW');
      v_count := v_count + 1;
    END;
  END FOR;

  COMMIT;
  o_processed := v_count;
  o_failed    := v_err;
END;
Security — Basics
XSUAA, OAuth2, JWT, scopes, roles — explained simply.
What is OAuth2 and how does it work in SAP BTP?Basic
  • OAuth2 is an industry-standard authorization framework — it allows apps to get access tokens securely
  • In SAP BTP, XSUAA is the OAuth2 authorization server
  • Simple flow (Authorization Code for browser apps):
  • User opens my Fiori app → browser redirects to XSUAA login page
  • User enters their credentials → XSUAA authenticates them
  • XSUAA redirects back with an authorization code
  • My app exchanges the code for an access token (JWT)
  • My app uses this JWT on every API request to my CAP service
  • CAP validates the JWT and checks the user's permissions
  • For machine-to-machine (no user): Client Credentials flow — app uses clientid + clientsecret to get a token directly
What is a JWT token and what does it contain?Basic
  • JWT = JSON Web Token — a digitally signed token that carries user information
  • It has 3 parts separated by dots: header.payload.signature
  • The payload contains claims — key-value pairs of information about the user
  • Important claims in a BTP JWT:
  • sub — unique user ID (subject)
  • scope — list of permissions the user has (e.g., my-app.orders.read)
  • iss — issuer — the XSUAA URL that created this token
  • exp — expiry timestamp — when the token becomes invalid
  • zid — zone/tenant ID — which tenant the user belongs to
  • email, given_name, family_name — user profile info
  • The signature ensures nobody tampered with the token — CAP verifies this on every request
  • I can decode the payload part (it is just base64) at jwt.io to debug issues
What is the difference between Scope, Role Template, and Role Collection?Basic
  • Scope — the smallest unit of permission. Like a single key that opens one door. Defined in xs-security.json
  • Example: my-app.orders.read — permission to read orders
  • Role Template — groups multiple scopes together. Like a keyring with multiple keys
  • Example: "OrderViewer" role template has scopes: orders.read + products.read
  • Role Collection — groups multiple role templates together. Assigned to actual users in BTP cockpit
  • Example: "Procurement Viewer" role collection contains the "OrderViewer" and "SupplierViewer" role templates
  • Chain: Scope → Role Template → Role Collection → Assigned to User → Appears in JWT
  • When a user gets 403 Forbidden: I check their JWT scopes and trace back through this chain to find what is missing
How do I add authorization to a CAP service?Basic
  • I add authorization at two levels in CDS: service level and entity level
  • Service level — requires any authenticated user to access the service:
service OrderService @(requires: 'authenticated-user') {
  // all entities require login
}
  • Entity level — specific roles needed for specific operations:
service OrderService @(requires: 'authenticated-user') {
  entity Orders @(restrict: [
    { grant: 'READ',   to: 'Viewer' },
    { grant: ['READ', 'WRITE', 'CREATE'], to: 'Editor' },
    { grant: '*',      to: 'Admin'  }
  ]) as projection on db.Orders;
}
  • CAP checks if the user's JWT scopes match the required role automatically — no custom code needed
  • If the user does not have the required scope → CAP returns 403 Forbidden automatically
  • The role names (Viewer, Editor, Admin) must match the role template names in xs-security.json
What is the difference between Authentication and Authorization?Basic
  • Authentication = Who are you? Verifying identity. Like showing your ID card
  • Authorization = What can you do? Checking permissions. Like checking if your ID card allows access to this room
  • In SAP BTP:
  • Authentication is done by XSUAA/IAS — user logs in and gets a JWT token
  • Authorization is done by CAP using the scope claim in the JWT — checks what the user is allowed to do
  • Example: I am authenticated (I logged in successfully) but I am not authorized to delete orders (my JWT does not have the delete scope) → I get 403 Forbidden
  • Both are needed. Authentication without authorization = anyone logged in can do anything
Security — Advanced
Principal propagation, IAS, JWT validation, secure custom endpoints.
What is principal propagation and when do I use it?Intermediate
  • Principal propagation = passing the end user's identity from my BTP app to a downstream system (like S/4HANA)
  • Without it: S/4HANA would see all requests as coming from a generic technical service user — bad for audit trails and authorization
  • With it: S/4HANA sees the actual user and applies their specific S/4HANA permissions
  • How it works technically:
  • User's JWT → XSUAA exchanges it for a SAML assertion (token exchange)
  • My CAP service passes this SAML assertion to S/4HANA via the destination
  • S/4HANA maps the SAML NameID to an S/4HANA user account
  • S/4HANA executes the request as that specific user
  • In SAP Cloud SDK: just pass the user's JWT — SDK handles the rest: .execute({ destinationName: 'S4', jwt: req.headers.authorization.split(' ')[1] })
  • Requires: SAML trust configuration between XSUAA and S/4HANA, and matching user accounts
What is the difference between IAS and XSUAA?Intermediate
  • XSUAA (Extended Services for UAA) — BTP's authorization server. Issues OAuth2 tokens. Manages scopes and role collections
  • IAS (Identity Authentication Service) — SAP's modern Identity Provider. Handles the actual user login experience
  • How they work together: IAS authenticates the user (verifies username/password or social login) → passes the identity to XSUAA → XSUAA issues the OAuth2 token with scopes
  • IAS supports: Single Sign-On (SSO), MFA, social logins (Google, LinkedIn), custom login pages
  • XSUAA alone does authentication too but IAS gives more flexibility for enterprise identity scenarios
  • In modern BTP apps: IAS → XSUAA trust is the recommended setup for external users
  • Internal users can still use XSUAA directly with company LDAP/AD federation
Scenario: Users get 401 Unauthorized after deployment. How do I debug step by step?Scenario
  • Step 1: Check if XSUAA service is bound — run cf env my-app and look for xsuaa in VCAP_SERVICES. If missing → rebind the service
  • Step 2: Get the failing request's Authorization header from browser DevTools (Network tab). Decode the JWT at jwt.io. Check:
  • Is the iss (issuer) URL matching my XSUAA tenant URL?
  • Is the aud (audience) matching my app's clientid?
  • Is the exp (expiry) in the future? (Token not expired)
  • Step 3: Check if xsappname in xs-security.json changed during deployment — old tokens have scopes with old xsappname prefix
  • Step 4: Check CF application logs: cf logs my-app --recent — look for token validation error messages
  • Step 5: Check if the XSUAA service plan changed — application vs broker plans have different capabilities
  • Fix: Usually rebind XSUAA service, re-deploy with correct xs-security.json, or clear user sessions so fresh tokens are obtained
Node.js
Async patterns, middleware, performance, memory leaks.
What is async/await and why is it important in CAP handlers?Basic
  • Node.js is single-threaded — it cannot block while waiting for database or API calls
  • async/await lets me write asynchronous code that looks synchronous — easy to read and maintain
  • All CAP handlers must be async because database queries are asynchronous operations
  • Without async/await I would need nested callbacks ("callback hell") — very hard to maintain
  • Rules I follow:
  • Always await database calls: const order = await SELECT.one.from('Orders')...
  • Always wrap in try-catch to handle errors gracefully
  • Do not await inside a forEach — use for...of loop instead
  • For truly independent operations use Promise.all — but be careful with HANA transactions
// WRONG — forEach does not wait for async ops
orders.forEach(async (order) => {
  await processOrder(order); // This runs in parallel uncontrolled!
});

// CORRECT — for...of waits sequentially
for (const order of orders) {
  await processOrder(order);
}
How do I detect and fix a memory leak in a CAP Node.js service?Advanced
  • Symptom: App memory usage grows slowly every hour → app crashes with OOM (Out of Memory) → CF restarts it
  • Most common causes in CAP:
  • Module-level Map or Array that grows forever (no size limit or eviction)
  • EventEmitter.on() called inside a request handler — adds a new listener on every request
  • Closures holding references to large objects that never get garbage collected
  • How to find it:
  • Take two heap snapshots 30 minutes apart using Chrome DevTools Memory tab
  • Compare — look for objects that increased in count (especially Map entries, Arrays)
  • Fix: Replace unbounded Map/Array with LRU cache:
// LEAKY — no eviction
const cache = new Map(); // grows forever!

// FIXED — max 500 entries, 5 minute TTL
const LRU = require('lru-cache');
const cache = new LRU({ max: 500, ttl: 1000 * 60 * 5 });
What is middleware in Express.js and how do I add it to a CAP service?Basic
  • Middleware is a function that runs for every HTTP request before it reaches the route handler
  • Common uses: logging, authentication checks, request parsing, rate limiting, CORS headers
  • CAP uses Express.js internally — I add custom middleware in server.js using cds.on('bootstrap')
  • Middleware must call next() to pass the request to the next middleware/route, or send a response to stop processing
// server.js — add custom middleware to CAP

cds.on('bootstrap', (app) => {

  // Logging middleware — runs on every request
  app.use((req, res, next) => {
    console.log(`${new Date().toISOString()} ${req.method} ${req.url}`);
    next(); // pass to next middleware
  });

  // Custom REST endpoint (not OData)
  app.get('/health', (req, res) => {
    res.json({ status: 'ok', timestamp: new Date() });
  });
});

What is data binding in UI5 and what are the types?Basic

What is the ODataModel V4 in UI5 and how does it differ from V2?Intermediate
  • ODataModel V2 (sap.ui.model.odata.v2.ODataModel) — older model, batch requests via $batch, auto-batch by default, client-side metadata caching
  • ODataModel V4 (sap.ui.model.odata.v4.ODataModel) — newer model, async-first, supports late property requests, server-driven paging, and OData V4 features like $apply
  • Key differences for interviews:
  • V4 uses synchronizationMode: "None" — no automatic sync, all operations are explicit
  • V4 supports $$ownRequest: true — a binding sends its own request, not batched
  • V4 has refresh() on individual bindings, not global refresh like V2
  • V4 does not support two-way binding by default — use $$updateGroupId for batch saves
  • Fiori Elements (FE) V4 (sap.fe) only works with OData V4 model

  "sap/ui/core/UIComponent",
  "sap/ui/Device",
  "./model/models"

What is an MTA and why do I use it instead of just cf push?Basic

How does blue-green deployment work and why is it important?Intermediate
  • Blue-green = running the OLD version (blue) and NEW version (green) of my app at the same time during deployment
  • Users stay on blue while green is being deployed and tested
  • Once green is healthy → traffic switches from blue to green
  • If green fails → traffic stays on blue. No downtime, no user impact
  • How to do it on CF:
cf deploy my-app.mtar --strategy blue-green
  • CF deploys to a temporary URL (my-app-idle.cfapps.region.hana.ondemand.com)
  • Runs health checks on the new version
  • If health checks pass → routes production traffic to new version
  • Old version is stopped and deleted
  • Requirements for blue-green to work:
  • App must be stateless — no data stored in app memory (all in HANA)
  • New DB schema must be backwards compatible — old app version must still work with new schema
  • Must have a /health endpoint that returns 200 when app is ready
Scenario: A deployment fails halfway. How do I recover without data loss?Scenario
  • Step 1 — Check if there is a stuck deployment operation: cf mta-ops
  • Step 2 — Abort the stuck operation if found: cf deploy --abort
  • Step 3 — Check what deployed successfully: cf apps and cf mtas
  • Step 4 — Find the root cause from logs:
  • HDI module failed → cf logs my-app-db --recent → look for SQL errors in .hdb files
  • Server module failed → cf logs my-srv --recent → look for startup errors (missing env var, binding issue)
  • Step 5 — Fix the issue in code/config, rebuild (mbt build), redeploy
  • Step 6 — If the previous running version was not affected, it continues serving users during this time
  • NEVER use cf undeploy --delete-services in production — this deletes ALL services including your HANA data!
  • Add the root cause and fix to a post-incident report and improve pre-deployment testing to prevent recurrence

What is the Connectivity Service and Cloud Connector?Basic

How do I implement circuit breaker for S/4HANA calls using Cloud SDK?Advanced

  • Without it: if S/4HANA is slow (10s timeout), every user request waits 10s and users see a frozen UI

  • 3 states: CLOSED (working normally) → OPEN (failing fast) → HALF-OPEN (testing recovery)

const breaker = new CircuitBreaker(
  async (bpId, jwt) => BusinessPartnerApi.requestBuilder()
    .getByKey(bpId).execute({ destinationName: 'S4', jwt }),
  {
    timeout: 5000,                 // fail if > 5 seconds
    errorThresholdPercentage: 50,  // open after 50% failures
    resetTimeout: 30000            // try again after 30 seconds
  }
);

// Fallback when circuit is open
breaker.fallback((bpId) => ({ bpId, name: 'Unknown (service unavailable)' }));

// Use in handler
this.on('getCustomer', async (req) => {
  const result = await breaker.fire(req.data.bpId,
    req.headers.authorization?.split(' ')[1]);

OData V2 vs V4
Differences, query options, batch, and CAP compatibility.
What are the key differences between OData V2 and V4?Basic
  • CAP natively produces OData V4 — V4 is the current standard
  • V2 is older — still used in some legacy Fiori apps built before 2018
  • Key differences:
  • V4 uses JSON by default. V2 defaults to XML (though JSON is supported)
  • V4 has $apply for server-side aggregation (GROUP BY, SUM, COUNT). V2 does not
  • V4 uses $count=true. V2 uses $inlinecount=allpages
  • V4 response: data in value array. V2 response: data in d.results array
  • V4 has cleaner URL for actions: /submitOrder. V2 uses: /Namespace.FunctionName
  • To expose V2 endpoint from CAP (for legacy UI5 apps), I add the V2 adapter proxy middleware
  • For all new UI5 development I use the V4 ODataModel from sap.ui.model.odata.v4
What OData query options do I use most and what do they do?Basic
  • $filter — filter rows by condition. CAP translates to SQL WHERE clause
  • $select — choose only specific fields. Reduces response size significantly
  • $expand — include related entity data (like SQL JOIN)
  • $orderby — sort results ascending or descending
  • $top — limit number of results returned (like SQL LIMIT)
  • $skip — skip N results for pagination (like SQL OFFSET)
  • $count=true — include total record count in response (for pagination UI)
  • $apply (V4 only) — server-side aggregation: sum, count, group by

GET /Orders?$expand=items($select=product,quantity)

GET /Orders?$top=20&$skip=40&$count=true

Webhooks & REST APIs

What is a webhook and how do I receive one in a CAP service?Basic
  • A webhook is an HTTP POST sent by an external system to notify my app when something happens
  • Example: GitHub sends a webhook to my app when code is pushed. Stripe sends one when payment is received
  • Unlike polling (my app checks every minute), webhooks are event-driven — external system calls me
  • 3 golden rules for webhook handlers:
  • Respond quickly — always return HTTP 200 within 5 seconds or the sender retries. Do heavy processing async
  • Verify the signature — check the HMAC signature in the header to ensure the sender is genuine
  • Be idempotent — same webhook delivered twice should not create duplicate data
// server.js — receive webhook from GitHub
cds.on('bootstrap', (app) => {
  app.use('/webhook', require('express').raw({ type: '*/*' }));

  app.post('/webhook/github', (req, res) => {
    // 1. Verify signature
    const expected = 'sha256=' + require('crypto')
      .createHmac('sha256', process.env.WEBHOOK_SECRET)
      .update(req.body).digest('hex');
    if (req.headers['x-hub-signature-256'] !== expected) {
      return res.status(401).json({ error: 'Invalid signature' });
    }
    // 2. Respond immediately
    res.status(200).json({ received: true });
    // 3. Process async (don't block the response)
    processWebhookAsync(JSON.parse(req.body.toString()));
  });
});

What is SAP Event Mesh and why do I use it instead of direct API calls?Basic
  • SAP Event Mesh is a managed message broker on BTP — like a post office for app-to-app messages
  • Problem with direct API calls: If System A calls System B directly and B is down → A also fails or waits

  • Resilience — messages queue up safely if the consumer is down
  • Decoupling — System A does not need to know about System B at all
  • Scalability — multiple consumers can read from the same topic
  • Guaranteed delivery — messages are not lost even if the broker temporarily goes down

How would you design a multi-tenant SaaS app on SAP BTP?Advanced

  • My approach using CAP MTXS (Multi-Tenancy Extension Services):
  • One CAP application deployment on CF — shared by all tenants
  • Each tenant gets a dedicated HDI container in HANA — completely separate schema
  • Tenant A's data CANNOT be accessed by Tenant B — guaranteed by separate schemas

  • New customer subscribes via BTP SaaS Registry
  • MTXS module automatically creates a new HDI container for that tenant

  • CF autoscaler scales the shared app based on load — all tenants benefit from scaling
How do I implement caching properly in a CAP application?Intermediate
  • Caching stores frequently read, rarely changed data in memory to avoid repeated database queries
  • Good for: product catalogs, configuration data, currency codes, lookup tables
  • Rule 1 — Always use LRU cache (not plain Map): Plain Map has no eviction — causes memory leaks
  • Rule 2 — Set TTL (Time-To-Live): Cached data should expire after N minutes to stay fresh
  • Rule 3 — For multi-instance CF apps use Redis: In-memory cache is per-instance; Redis is shared across all instances

  const key = `products_${JSON.stringify(req.query)}`;
  const cached = productCache.get(key);
  if (cached) return cached;

  const result = await SELECT.from('Products');
  productCache.set(key, result);
  return result;
});

What is the N+1 query problem and how do I fix it in CAP?Intermediate
  • N+1 problem = fetching N records, then making N more individual queries to get related data
  • Example: fetch 100 orders (1 query), then for each order fetch the customer name (100 more queries) = 101 queries total!

    o.customerName = cust?.name;
  }
});

// FIX 1 — Batch query (one query total)

  const ids = [...new Set(orders.map(o => o.customerId))];
  const custs = await SELECT.from('Customers').where({ ID: { in: ids } });
  const map = Object.fromEntries(custs.map(c => [c.ID, c.name]));
  orders.forEach(o => { o.customerName = map[o.customerId]; });
});

Write a rate limiter middleware — max 100 requests per minute per user.Coding
  • Track: user ID → { count, window start time }
  • On each request: if window expired → reset counter. Else increment and check limit
  • Return 429 with Retry-After header when limit exceeded
  • For multi-CF-instance apps: use Redis instead of in-memory Map (each instance has separate memory)
const rateLimitStore = new Map();

function rateLimiter(maxReq = 100, windowMs = 60000) {
  return (req, res, next) => {
    const userId = req.authInfo?.getLogonName() || req.ip;
    const now = Date.now();
    const record = rateLimitStore.get(userId);

    if (!record || now - record.start > windowMs) {
      rateLimitStore.set(userId, { count: 1, start: now });
      return next();
    }

    record.count++;
    res.setHeader('X-RateLimit-Limit', maxReq);
    res.setHeader('X-RateLimit-Remaining', Math.max(0, maxReq - record.count));

    if (record.count > maxReq) {
      const retryAfter = Math.ceil((record.start + windowMs - now) / 1000);
      return res.status(429).json({ error: 'Too many requests', retryAfter });
    }
    next();
  };
}

cds.on('bootstrap', (app) => {
  app.use('/odata/', rateLimiter(100, 60000));

  // Cleanup expired entries every 5 min
  setInterval(() => {
    const cutoff = Date.now() - 60000;
    for (const [user, r] of rateLimitStore)
      if (r.start < cutoff) rateLimitStore.delete(user);
  }, 300000);
});

this.on('calculateOrderTotal', async (req) => {
  const { orderId } = req.data;

  // 1. Validate input
  if (!orderId) return req.error(400, 'orderId is required');

  // 2. Fetch order
  const order = await SELECT.one.from('Orders')
    .where({ ID: orderId });
  if (!order)             return req.error(404, 'Order not found');
  if (order.status === 'CANCELLED')
    return req.error(409, 'Cannot price a cancelled order');

  // 3. Fetch line items
  const items = await SELECT.from('OrderItems').where({ order_ID: orderId });
  if (!items.length)      return req.error(422, 'Order has no items');

  let pricingResult;

      customerId: order.customerId,
      items: items.map(i => ({ sku: i.productId, qty: i.quantity }))
    });
  } catch(err) {
    req.logger.error('Pricing API failed:', err);
    return req.error(502, 'Pricing service unavailable — please try again');
  }

  // 5. Calculate and save
  const total = pricingResult.items.reduce((s, i) => s + i.totalPrice, 0);
  await UPDATE('Orders').set({ totalAmount: total }).where({ ID: orderId });

  // 6. Return result
  return { orderId, totalAmount: total, currency: pricingResult.currency };
});

SELECT TOP 5
  c.ID           AS CUSTOMER_ID,
  c.NAME         AS CUSTOMER_NAME,
  COUNT(o.ID)    AS ORDER_COUNT,
  SUM(o.TOTAL_AMOUNT) AS TOTAL_VALUE,
  AVG(o.TOTAL_AMOUNT) AS AVG_ORDER_VALUE
FROM ORDERS o
INNER JOIN CUSTOMERS c ON o.CUSTOMER_ID = c.ID
WHERE
  o.STATUS NOT IN ('CANCELLED', 'DRAFT')
  AND o.CREATED_AT >= ADD_DAYS(CURRENT_DATE, -30)
GROUP BY c.ID, c.NAME
ORDER BY TOTAL_VALUE DESC;
  • For performance: I would ensure a composite index exists on ORDERS(STATUS, CREATED_AT, CUSTOMER_ID)
  • HANA uses ADD_DAYS — not DATEADD like SQL Server

Rapid Revision Notes
One-liner definitions — memorize before walking into the interview.
CAP / CDS
CAP: Convention-over-configuration Node.js framework. Define CDS entities → get OData APIs, HANA tables, auth, and CRUD automatically.
Association vs Composition: Association = loose FK (entities exist independently). Composition = parent owns child (cascade delete, deep insert, draft).
before / on / after: before = validate input. on = replace default handler. after = enrich response. Never skip knowing which you need.
Deep insert: POST parent + children in one request. Only works for Compositions. CAP handles UUIDs and FKs automatically.
Draft: @odata.draft.enabled → auto-save in HANA DRAFT schema. SAVE event = final validation before activate.
Virtual field: NOT in DB. Computed in after READ handler. Calculated field = SQL expression computed by HANA.
Projection: Service-layer view on entity. Hides sensitive fields, restricts columns, adds computed fields. Always use in public APIs.
Aspect: Reusable mixin. entity Orders : managed → adds createdAt, createdBy, modifiedAt, modifiedBy automatically.
Security
XSUAA flow: User logs in → XSUAA issues JWT → JWT has scope claim → CAP checks scope vs @restrict → allow or 403.
Authorization chain: Scope → Role Template → Role Collection → User. Debug 403 by decoding JWT at jwt.io and tracing this chain.
JWT claims: sub (user ID), scope (permissions), iss (issuer/XSUAA URL), exp (expiry), zid (tenant ID).
Principal propagation: User JWT → XSUAA SAML exchange → S/4HANA sees the real user. Adds latency — cache the SAML assertion.
Auth vs AuthZ: Authentication = who are you? Authorization = what can you do? Both are always needed.
Client Credentials flow: Machine-to-machine. No user. App uses clientid + clientsecret to get a token directly from XSUAA.
HANA
HDI container: Isolated HANA schema per app/tenant. Declarative deployment via .hdb files. No manual CREATE TABLE scripts.
Column store: HANA's default. Great for analytics. Row store = for very high write-frequency tables only.
Slow query steps: M_EXPENSIVE_STATEMENTS → EXPLAIN PLAN → add index → UPDATE STATISTICS → Calculation View.
Index tip: Index columns in WHERE, JOIN, and ORDER BY. Put equality columns first in composite index, range/sort columns last.
Cloud Foundry
MTA: Bundles all modules + services in one .mtar archive. Deploy with cf deploy app.mtar. Handles creation order automatically.
Blue-green: Deploy new version alongside old → health check → switch traffic → delete old. Requires stateless app + backwards-compatible schema.
VCAP_SERVICES: CF injects all service credentials here. CAP reads it automatically. Never hardcode credentials in code.
Event Mesh / Integration
Event Mesh: Managed AMQP message broker. Queues = one consumer. Topics = multiple consumers. Decouples services.
Outbox pattern: Write event to DB table IN SAME TRANSACTION as business data. Background job publishes to broker. No lost events.
Circuit breaker: CLOSED (normal) → OPEN (fail fast after threshold) → HALF-OPEN (one test request) → back to CLOSED or OPEN.
Webhook rules: 1. Verify HMAC signature. 2. Respond 200 in under 5 seconds. 3. Process async. 4. Be idempotent.
Performance
N+1 fix: Replace per-record SELECT in a loop with one SELECT WHERE ID IN (list). Or use $expand for CAP to generate a JOIN.
Always set query limit: @cds.query.limit: { default: 50, max: 200 }. Prevents users from accidentally loading millions of rows.
Memory leak: Plain Map = leak (no eviction). Always use LRU cache with max size and TTL. Check with heap snapshot comparison.
